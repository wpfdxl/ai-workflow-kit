# 用户资料查询 需求

> 阶段：①（示例样板，栈：Go 1.25 / Kratos / DDD）

## 1. 需求背景

- 一句话目标：用户服务提供「按用户 ID 查询资料」的只读 RPC/HTTP 接口，供 BFF 与其它微服务调用
- 业务方/提出人：示例
- 期望上线时间：—

## 2. 涉及端

- [x] Web（HTTP JSON，由 proto 注解暴露）
- [x] 内部服务 / RPC（gRPC）
- [ ] 管理后台
- [ ] 其他：

## 3. 需求描述

用户中心微服务需对外暴露查询能力：根据 `user_id` 返回昵称、头像 URL、状态。不存在时返回明确业务错误（非 500）。本需求不包含注册、改资料、鉴权签发。

## 4. 功能点拆解

- [x] 功能点1：`GetUserProfile` — 入参 user_id，出参资料字段
- [x] 功能点2：用户不存在 → 业务错误码 `USER_NOT_FOUND`
- [x] 功能点3：user_id 非法（≤0）→ 参数错误

## 5. 输入输出预期

- 关键入参：`user_id` int64，必填，>0
- 关键返回字段：`user_id`、`nickname`、`avatar_url`、`status`（1 正常 / 2 冻结）
- 特殊展示：无脱敏要求（示例）；空态用错误码而非空对象冒充成功

## 6. 验收标准

- [x] proto 定义与 HTTP/gRPC 均可调通（示例文档层）
- [x] 分层符合 DDD：查询编排在 biz，存储在 data
- [x] 错误码稳定，调用方可依赖

## 7. 已知约束 / 参考

- 数据来源：用户表（示例名 `users`），字段以方案为准
- 参考的现有接口/功能：无（绿场示例）
- 性能/量级要求：单次查询；可加短 TTL 缓存（可选）
- ❓ 缓存是否一期要做：示例方案里做「可选，默认不做」
